<objective>
Build the backend data layer for App Shell & Settings: the `modules` table (CORE-07
runtime enable/disable state) and the key-value `settings` table (CORE-06 company info +
locale defaults), their idempotent seeds, a single Alembic revision, and the new

always-on enforcement — reads from these two tables. They are the shared foundation; the
API router plan (03-02) and frontend plan (03-03) depend on them existing.

modified auth seed (new permission), and a `backend/tests/core/` test package.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/v1/core/* | Untrusted HTTP request body and path params cross into settings/module mutation logic |
| seed (system) → DB | Startup seed writes platform rows (modules, settings, permissions) with no human actor |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Elevation of Privilege | `settings` table `owner_id`/`scope` columns | mitigate | Server always sets `scope="global", owner_id=None` in the seed; `owner_id` is never a client-settable field in v1 (no per-user write path exists yet). Schema groundwork only. |
| T-03-02 | Tampering | `always_on` flag on `modules` | mitigate | `always_on` is set only by the seed (SYERP=True); there is no API to mutate `always_on`. The disable-guard is enforced at the API layer in 03-02 (T-03-04). |
| T-03-03 | Tampering | `settings:manage` permission grant | mitigate | Permission granted to the `admin` role only; explicitly excluded from `_USER_ROLE_PERMS` so standard users cannot reach settings/module endpoints (gates live in 03-02). |
| T-03-09 | Spoofing/Tampering | partial unique index `uq_settings_global` | accept | Without the partial index, duplicate global settings rows could silently coexist (Postgres NULL!=NULL); index prevents this. Low residual risk once index ships. |
</threat_model>
