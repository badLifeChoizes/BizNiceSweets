## Critical Blockers

### 1. `SyerpPartner` → `Partner` — one bug, breaks PLUM-07 & PLUM-10 (BLOCKER)
`backend/app/modules/plum/service.py` imports a class that does not exist:
```python
from app.modules.syerp.models import SyerpPartner   # ImportError — class is `Partner`
```
at **4 call sites**: line 1634 (`add_avl_link`), 2139 (`build_json_export`), 2607 (`validate_import`), 2740 (`commit_import`).

Live-reproduced against the running stack:
- `POST /api/v1/plum/parts/{id}/avl` → **HTTP 500** (`ImportError: cannot import name 'SyerpPartner'`)
- `POST /api/v1/plum/import/validate` with an AVL entry → **HTTP 500** (same)

The FK (`plum_avl_link.vendor_id → syerp_partner.id`), Pydantic schemas, and frontend `AvlLinkSheet` are all correct — only the service layer never executes. Backend tests `test_avl.py::test_add_avl_link` and `test_import_export.py::test_import_preview_unknown_vendor` are written to catch this but are `skip_if_no_db` and were never run against a live database.

**Fix:** rename `SyerpPartner` → `Partner` (or add an alias import) at all 4 sites. One-line-per-site.

### 2. Part-number generator lexicographic MAX (BLOCKER for auto-numbering, PLUM-01)
`generate_part_number()` (service.py:108-136) does `SELECT MAX(part_number) WHERE part_number LIKE 'P%'` on a VARCHAR column, then increments in Python. Past a digit-width boundary, string MAX returns a stale value (`"P100000" < "P99999"`), so the generator hands back an already-used number → duplicate-key 500 on the next create. The documented single-retry mitigation doesn't help — the bug is deterministic. Live-reproduced on the current instance (which has prototype data past the threshold). Explicit `part_number` entry still works as a workaround.

**Fix:** order by numeric suffix (`CAST(SUBSTRING(part_number, 2) AS INTEGER)`) or track a sequence, not string MAX.
