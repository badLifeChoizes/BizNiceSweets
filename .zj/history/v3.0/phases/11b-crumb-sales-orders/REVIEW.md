# Review: Phase 11b — CRUMB sales orders + soft-reservation (a8191cf..HEAD)
Date: 2026-07-17

## Findings   <!-- ranked most severe first -->

### 1. [blocker] Soft-reservation is unreachable through the UI — every directly-created SO line is non-stock and reserves 0
- **Where:** frontend `SalesOrderLineEditor.tsx:83-99` and `SalesOrderDetailLines.tsx:228-241` (both `handleAdd`); backend `service/sales_orders.py:118-133` (`_build_line_kwargs`) + `:196-197` / `:412-428` (create / add_line copy `line.item_id` verbatim, no `plum_part_id`→`item_id` resolution).
- **Failure:** Both frontend add paths (the create dialog's line editor and the detail-screen add form) only ever send `{ plum_part_id, qty_ordered, unit_price }` or `{ description, ... }` — they **never send `item_id`**, and there is no UI to pick a stock item. The backend's direct-create/add-line path (unlike `convert_quote_to_sales_order`, which calls `_resolve_item_id_for_part`) does **not** resolve `plum_part_id`→`item_id`. Concrete: a user creates an SO for 10 units of a PLUM part that has 100 on hand and a linked `InventoryItem`, then confirms. The line is persisted with `item_id = NULL`, so `confirm_sales_order` treats it as non-stock (`line.item_id is None → qty_reserved = 0`). The detail grid shows **Reserved 0 / Shortage 10** and badges the part line **"Non-stock"** — regardless of available stock. SC4 (the phase's headline feature) is functional only for quote-conversion-created lines; the primary create/add UI flow (SC2/SC6) reserves nothing. The backend `verify_crumb_so.py` masks this because it passes `item_id=item_e` directly to `SalesOrderLineCreate` (`:698-699`, `:723-724`), which no UI path does.
- **Fix:** Resolve `item_id` from `plum_part_id` on the direct-create and add-line paths too — reuse `_resolve_item_id_for_part` inside `_build_line_kwargs`/`create_sales_order`/`add_line` (symmetry with conversion), or have the frontend resolve and send `item_id`. Add a frontend/API test that creates a part-linked line via the create/add path, confirms, and asserts `qty_reserved > 0`.

## Questions

- **Accepted quote can be converted to an SO an unlimited number of times.** `convert_quote_to_sales_order` requires `quote.status == "accepted"` but never changes the quote's status (accepted is terminal in `QUOTE_TRANSITIONS`), and the "Convert to Sales Order" button stays visible on every accepted quote. Two clicks (or two users) produce two distinct SOs both stamped `source_quote_id = quote.id`. The frontend hook doc (`hooks.ts:678-680`) asserts the quote "status moves to converted," which does not happen — suggesting a guard was intended. Is repeated conversion by design (one quote → many orders), or should conversion be idempotent / gated? Not filed as a defect because the PLAN does not forbid multiple conversions.
