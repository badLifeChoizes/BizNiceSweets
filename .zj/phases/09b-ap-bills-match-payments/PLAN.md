# Plan: Phase 09b — AP bills, PO match & payments
Goal: A user can create a vendor bill by pulling that vendor's unbilled PO receipts, post it (Dr GR/IR + Dr expense, Cr AP — one balanced JE via the 09a engine), and record full/partial payments (Dr AP / Cr chosen cash-or-bank), with a server-enforced Draft→Posted→Paid lifecycle, overpayment rejected, and every mutation audited and RBAC-gated.
Status: ready
Branch: `feature-syerp-ap-bills`, cut off the verified 09a tip (current `feature-syerp-gl-posting-engine` HEAD; tagged `zj/good-09a-gl-posting-engine`) — D-P9b-8.

## Success criteria
<!-- From the phase brief; each implements a SYERP-12 acceptance criterion, noted inline. -->
- **SC1** (AC4): A vendor bill is created receipt-driven — for a chosen vendor the API surfaces PO lines carrying unbilled received qty (`qty_received − Σ already-billed matched_qty`); the user bills selected lines. A matched line MUST bill exactly `unbilled_received_qty × PO-line unit_cost` (exact match, D-P9b-2) or the bill create/edit is rejected 4xx (no price-variance account in 9b).
- **SC2** (AC4): A bill can also carry non-PO lines (D-P9b-3), each with a user-chosen EXPENSE/ASSET GL account and a positive amount.
- **SC3** (AC4): Posting a bill posts ONE balanced JE via `post_journal_entry` (`commit=False`, shared transaction): Dr GR/IR 2150 for each matched line + Dr <chosen account> for each non-PO line, Cr AP 2110 for the bill total. Bill lifecycle Draft→Posted→Paid is enforced server-side via a `BILL_TRANSITIONS` map (invalid transitions 4xx); the bill JE is source-linked (`source_type='ap_bill'`, `source_id=bill.id`) and append-only-consistent with the 09a immutability model.
- **SC4** (AC5): A payment against one or more posted bills posts Dr AP 2110 / Cr <chosen cash/bank>; open balance = billed − paid (each side `coalesce(sum,0)`, D-P8-4); overpayment (drives any bill's open balance negative) is rejected 4xx (D-P8-7 pattern); a bill auto-advances to Paid when its open balance hits zero. Payment JE source-linked (`source_type='ap_payment'`).
- **SC5** (AC4/AC5 UI): From the UI a user can create+match a bill, post it, and pay it (partial then full), reachable from `SyerpNav`; screens follow the existing PurchaseOrders / PurchaseOrderDetail + dialog patterns.
- **SC6** (AC8/AC9): Bill create, bill post, and payment each write an attributable audit event; ALL new endpoints are gated by `syerp:read` (GET) / `syerp:write` (mutations). Per the Phase 09a learning, audit-writes + RBAC live in the ROUTER, so an **HTTP-level** verify script (`verify_ap_api.py`) proves them — a service-level script cannot.

## Decisions (resolved at planning — D-P9b-1..5 in `.zj/DECISIONS.md`; two architect calls recorded here)
1. **Receipt-driven, PO-line-grain match (D-P9b-1).** Unbilled qty = `po_line.qty_received − Σ(matched BillLine.matched_qty for that po_line_id)`, summed across ALL posted-or-draft bills (a draft bill already reserves its matched qty so two drafts can't double-bill the same receipt). Each matched BillLine persists `po_line_id` + `matched_qty` + `unit_cost` — the billed-qty ledger.
2. **Exact match, no variance account (D-P9b-2).** A matched line is accepted only when `matched_qty == unbilled_received_qty` AND `unit_cost == po_line.unit_cost`; any variance is rejected 4xx. This guarantees the matched line's Dr GR/IR equals the receipt's original Cr GR/IR, so GR/IR clears to zero (the accounting crux, below). No price-variance GL account exists in 9b.
3. **Non-PO lines (D-P9b-3).** A non-PO BillLine carries a user-chosen `account_id` (must resolve to an EXPENSE or ASSET account — validated in service + schema) and a positive `amount`; posts Dr <account> / Cr AP.
4. **Payment credits a selectable cash/bank account (D-P9b-4).** Default 1110 Cash; SEED a new `1111 Bank – Checking` (ASSET, parent 1100 — NOT a liability). Posting Dr AP 2110 / Cr <chosen>.
5. **Auto-numbering + FSM (D-P9b-5).** Bills auto-number `BILL-####` (mirror `_next_po_number`), capture a free-text `vendor_invoice_ref`, and walk Draft→Posted→Paid via a `BILL_TRANSITIONS` map (PO_TRANSITIONS pattern). Auto-advance to Paid at zero open balance; overpayment 4xx (D-P8-7 pattern).
6. **Payment→bills allocation model (D-P9b-7).** Model payments as `Payment` (header: `payment_date`, `cash_account_id`, `amount`, `reference`, `actor_id`) + `PaymentAllocation` (`payment_id`, `bill_id`, `amount`) — one payment settles N bills. Rationale: SC4/AC5 says "against one or more posted bills," a real cheque/transfer commonly clears several vendor invoices at once, and the allocation grain is exactly what the open-balance derivation and overpayment guard need (per-bill `Σ allocation.amount`). A flat 1-payment→1-bill column would force N payments for one cheque and re-model later. `Payment.amount` MUST equal `Σ` its allocations (validated).
7. **Endpoint path spellings (D-P9b-7).** `POST /syerp/ap/bills`, `GET /syerp/ap/bills`, `GET /syerp/ap/bills/{id}`, `POST /syerp/ap/bills/{id}/post`, `GET /syerp/ap/unbilled-receipts?vendor_id={id}`, `POST /syerp/ap/payments`, `GET /syerp/ap/payments`. (Mirrors the `/syerp/gl/...` shape of D-P9a-3.)
8. **Branch base (D-P9b-8, owner-confirmed 2026-07-11).** Cut a fresh `feature-syerp-ap-bills` off the current 09a tip (`feature-syerp-gl-posting-engine` HEAD, tagged `zj/good-09a-gl-posting-engine`). 9b stacks on 9a's commits; each sub-phase keeps its own branch for a separate ship/PR; matches the "branch off the working tip" discipline. ## Risks
- **Double-billing a receipt (highest, correctness).** If `list_unbilled_receipts` / `create_bill` sum matched qty across only POSTED bills, two DRAFT bills can each claim the same received qty and over-bill GR/IR. Early warning: `verify_ap.py` (a/b) shows unbilled_qty not decreasing when a draft bill already reserved it. Mitigation: `_unbilled_qty` sums matched_qty across ALL non-cancelled bills (draft + posted); recompute live at both create and post time (never trust a stale draft snapshot).
- **GR/IR fails to clear (the phase crux).** If the exact-match guard is relaxed (or `unit_cost` drifts from the PO line), Dr GR/IR ≠ the receipt's Cr GR/IR and 2150 never returns to zero — silent AP/inventory mis-statement. Early warning: `verify_ap.py` (e) pre/post GR/IR balance differs. Mitigation: `_is_exact_match` enforced in service AND schema; the verify (e) assertion is the gate — do NOT weaken it to fit output (the exact defect class the broken DB-pytest, D-P7-4, would mask).
- **Split unit of work (atomicity).** A stray `commit=True` on the bill/payment `post_journal_entry`, or a `write_audit` (self-commits) called mid-service, would let a bill flip to Posted without its JE (or a payment persist without allocations). Mitigation: JE posted `commit=False`; the service owns the single commit; ALL audit writes happen in the router AFTER the service returns — exactly the receive/journal-post template (router.py:844/938).
- **RBAC/audit unproven by service tests.** Because RBAC + audit live in the router, `verify_ap.py` (service-level) cannot prove SC6 — only `verify_ap_api.py` (HTTP) can. Early warning: a green `verify_ap.py` with no `verify_ap_api.py`. Mitigation: Task 12 is a first-class gate, planned from the start (the Phase 09a learning).
- **Migration drift.** Hand-written 0010 diverging from the four models causes boot/autogenerate mismatch. Mitigation: Task 3 round-trips upgrade/downgrade/upgrade; criterion is "no NEW ap operations," accepting the pre-existing repo drift.

## Out of scope
- AP aging report + financial statements (Trial Balance, P&L, Balance Sheet) — Phase 9c.
- Price/quantity variance accounting on the match (exact-match only in 9b, D-P9b-2); 3-way match against a separate invoice-vs-PO-vs-receipt tolerance — not this phase.
- Editing or voiding a POSTED bill / reversing a payment (bills are FSM-forward only; a correction is a future credit-memo/reversal feature).
- Credit memos, vendor prepayments/deposits, early-payment discounts, multi-currency, tax lines on bills.
- GL account CRUD (CoA stays seeded/read-only) and period close / fiscal-period locking.
- Offline/Service-Worker support for the new screens (standing cross-module concern, not this phase).
